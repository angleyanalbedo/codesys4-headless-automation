# CODESYS 4 File-Based Project Format

## Project roots

CODESYS 4 stores projects as folders rather than one opaque project archive. The principal roots are:

| Root | Meaning |
|---|---|
| `*.fbslib` | source library project |
| `*.fbsdev` | device project |
| `*.fbsws` | workspace containing projects |
| `*.compiled-library-v3` | compiled library artifact |
| `*.fbslib.zip` | source library archive/packaging format |

The exact available formats depend on the installed CODESYS 4 version. Do not infer that a source archive is a compiled artifact.

## Library project layout

A library project normally has this shape:

```text
ControlLib.fbslib/
├── ProjectInfo.json
├── Libraries.json
├── Libraries.lock.json       # generated after resolution
├── FB_Motor.fb.st
├── AddOne.fn.st
└── .library-cache/           # local cache, usually not committed
```

`ProjectInfo.json` stores title, semantic version, author/company, namespace, description, and optional categories. Categories are display metadata such as `System|Motion`; they do not control dependency resolution.

## IEC source naming

CODESYS file-based storage uses predictable names:

| IEC object | ST filename |
|---|---|
| program | `Main.prg.st` |
| function block | `Motor.fb.st` |
| function | `Add.fn.st` |
| method | `Start.meth.st` |
| global variable list | `Globals.gvl` |
| interface | `IMotor.itf` |
| structure | `Position.struct` |
| enumeration | `State.enum` |
| alias | `Distance.alias` |

Structured Text is stored as plain source text. A typical program is:

```iecst
PROGRAM PLC_PRG
VAR
    nCounter : INT;
END_VAR

nCounter := nCounter + 1;
END_PROGRAM
```

Use UTF-8 without BOM and stable line endings. Graphical language implementations have their own serialized representation; an agent must not invent a Ladder/FBD implementation by writing ST syntax into a graphical object.

## Device application layout

A device project normally contains `Devices`, a project `ProjectInfo.json`, and an application folder such as `Application.iecapp^`. The caret-suffixed folder contains `Libraries.json`, `TaskConfiguration.json`, and the POU source files. The application folder is required for a build.

This is why a library smoke test cannot prove that a device application or a boot application builds. Use a valid device project and target/device description for that claim.

## Libraries.json and lockfile

`Libraries.json` is the developer-maintained direct dependency manifest. Its main sections are:

- `references`: namespace-to-reference dictionary;
- `placeholderOverrides`: explicit resolutions for placeholder libraries;
- `libraryParameters`: parameters passed to libraries.

Reference types include:

- `ManagedLibrary` with a library ID and version/pattern;
- `RelativePath` pointing to another `*.fbslib` project or compatible library path;
- `Placeholder` resolved by an override, component, extension, or device description.

`Libraries.lock.json` is generated by resolution. It records the concrete dependency graph and integrity information, including SHA384 data for compiled libraries. Commit it when reproducible builds are required.

The usual lifecycle is:

```text
edit Libraries.json
    -> c4-cli library resolve
    -> review Libraries.lock.json
    -> c4-cli library check
```
